# Правила bin-builder

## Зачем

Парк серверов — много разных дистрибутивов Linux и их версий, инфраструктура офлайн.
Держать пакеты под каждую ОС и строить вокруг этого ansible тяжело. Поэтому всё, что
можно, собираем из исходников в один бинарник с минимумом внешних зависимостей:
чем меньше он требует от системы, тем на большем числе ОС он запустится.

Цель — «надуть» бинарник по максимуму: вшить внутрь все библиотеки и все полезные
модули/фичи, чтобы на целевой машине не понадобилось ничего, кроме ядра.

100% покрытия не требуется. Если бинарник покрывает хотя бы часть ОС — это уже польза.
Несовместимые случаи отсечёт ansible, отдельно о них не заботимся.

## Структура

```
builds/<bin>/
  <bin>                # собранный бинарник (результат сборки, в git не хранится)
  Dockerfile           # рецепт сборки
  docker-compose.yml   # запуск сборки
  README.md            # название, версия, дата, оценка совместимости
```

Имя папки и имя бинарника совпадают. Новый рецепт начинается с копии `builds/0_template/`.

В git попадают только рецепты: `.gitignore` в `builds/*/` пропускает лишь `Dockerfile`,
`docker-compose.yml` и `README.md`. Если рецепту нужен ещё файл (например, патч),
добавьте для него исключение `!builds/*/<файл>` в `.gitignore`.

## Как собирать

**Dockerfile** — две стадии:

1. `builder` — `alpine` (musl), `--platform=linux/amd64`. Ставим `*-dev` и `*-static`
   пакеты всех зависимостей, качаем исходники, проверяем sha256, собираем с `-static`.
2. `export` — минимальный образ с бинарником, `CMD` копирует его в `/out`.

Правила рецепта:

- Версии — через `ARG` в начале, одно место для обновления.
- Исходники только с проверкой sha256: официальная `.sha256` от апстрима, а если её
  нет (GitHub-архивы) — сумма, посчитанная при добавлении рецепта, прямо в Dockerfile.
- `curl` с `--retry 5 --retry-all-errors`.
- Если в Alpine нет `.a` нужной библиотеки — собираем её из исходников статически
  в той же стадии `builder`, с отключением опций, которые тянут несобираемое.
- Включаем максимум функциональности (модули, расширения, сторонние модули), если
  они собираются статически.
- После сборки — `strip` и обязательные проверки, которые валят сборку:
  ```sh
  file <bin>
  ! readelf -l <bin> | grep -q INTERP    # нет динамического загрузчика
  ! readelf -d <bin> | grep -q NEEDED    # нет внешних .so
  ./<bin> --version                      # бинарник запускается
  ```
- Пути и умолчания (конфиги, логи, пользователь) — как у официальных пакетов апстрима,
  без привязки к именам, специфичным для одного дистрибутива.
- Если сборка падает в configure — выводить лог configure (`|| { tail ...; exit 1; }`).

**docker-compose.yml** — один сервис `build`: собирает стадию `export`
(`network: host` для сборки), монтирует папку рецепта в `/out`, запускается от
`${UID:-1000}:${GID:-1000}`. В конце файла — закомментированная шпаргалка сборки без кеша.

Сборка:

```sh
cd builds/<bin>
docker compose build && docker compose run --rm build
# без кеша:
docker compose build --no-cache && docker compose run --rm build
```

## Проверка

Перед тем как закоммитить, бинарник прогоняется на нескольких образах — старых и
новых, glibc и musl, например: `centos:7`, `debian:9`, `ubuntu:18.04`, `rockylinux:9`,
`opensuse/leap:15`, `busybox:musl`. Достаточно проверки конфига и простого запроса,
задействующего вшитые модули.

## README.md

Минимум информации:

```
# <bin> <version>

Дата сборки: YYYY-MM-DD

Совместимость: **N/10** — одна-две строки: что внутри, что осталось снаружи.
```

### Оценка совместимости

Субъективная ожидаемая оценка того, на скольких ОС бинарник запустится как есть.

| Оценка | Что значит |
|---|---|
| 10 | Полностью статический, ничего не требует от системы, кроме ядра; работает на любом x86_64 Linux. |
| 8–9 | Полностью статический, но есть мелкие ограничения: только amd64, нужны относительно свежие возможности ядра, зашитые умолчания (пользователь, пути), данные снаружи (mmdb, сертификаты). |
| 5–7 | Часть зависимостей осталась внешней, но они распространены везде (libc определённой минимальной версии, libstdc++). |
| 3–4 | Внешние зависимости, которые есть не на всех ОС или различаются по версиям. |
| 1–2 | Много внешних зависимостей под каждую ОС; бинарник почти ничего не выигрывает у пакета. |

## Неудачный или узкоприменимый кейс

Если уже на берегу видно, что эффективный бинарник не создать — не собираем. Признаки:

- ключевая часть — динамические плагины/модули (`dlopen`), интерпретатор со своей
  экосистемой пакетов (perl/python-модули), привязка к systemd/D-Bus/PAM/NSS;
- зависимости, которые принципиально не линкуются статически или тянут за собой
  графический стек;
- программа на деле требует установленного окружения (файлы данных, сервисы),
  и один бинарник ничего не решает;
- ожидаемая оценка ниже 3 — бинарник не выигрывает у пакета.

Тогда создаём папку только с `README.md`:

```
# <bin>

Не собран: кейс неудачный.

Причина: <почему эффективный бинарник не получится>.
```

Если бинарник собрать можно, но вшить удалось не всё (часть модулей отключена) —
собираем, а в README перечисляем, чего нет и почему, и снижаем оценку по таблице.
